# Evidence-backed JD-to-resume workflow

## 1. Parse the JD; establish provenance
- Read the actual JD from a supplied official posting URL or pasted text. If the live posting is inaccessible, use the user's pasted JD with an explicit **unverified-live-status** note, not invented requirements.
- Extract technical scope, responsibilities, seniority, location, hard qualifications, preferred skills and outcome expectations. Group repeated JD keywords; prioritize based on actual relevance, not keyword stuffing.

## 2. Compare all candidate source material
- Read all available user-supplied Base/Master Resume Google Docs plus Career Story Bank; preserve author, technologies, responsibility and time-frame distinctions.
- Select the most relevant Base (e.g. Backend, Cloud, AI) and explain the choice. Do not generate a new resume from scratch when a formatted source exists.
- Create an evidence table with **JD requirement / source quote or story / evidence confidence (direct, transferable, missing, unknown) / recommended treatment**. Do not turn familiarity into production ownership.

## 3. Show an edit proposal before writing
- Prioritize modest ATS-aligned edits that clarify existing truthful achievements. Preserve technical detail and all substantial original bullets.
- For every **whole-bullet rewrite, deletion, section move, achievement change, or Skills addition implying new experience**, show exact current text and exact proposed replacement and wait for explicit approval. Supported tiny keyword insertions are still subject to any user-imposed approval boundaries.
- Keep concrete scale/outcome numbers only when supported by source evidence. Don't claim model-training ownership, cloud KMS mechanisms, invented 100% coverage, specific availability, etc., without proof.
- Honor user preferences for unchanged bullets, one-page layout, named base, file naming, versioning and ATS keywords. Do not silently sacrifice formatting for match score.

## 4. Copy, then make only approved scoped changes
- Use the authorized Google Docs/Drive connector to copy the selected native document into the user's specified output folder; **never modify the base file**.
- Apply literal, guarded edits to the **new** Doc only, preserving fonts, sizes, margins, paragraph spacing, indentation, heading hierarchy and any existing highlights/links. Check that intended text occurrences changed exactly once.
- Read changed sections and surrounding bullets back. Do not claim successful writes until connector confirms and results are verified.

## 5. PDF verification
- Export the edited native Google Doc to PDF only with working tools. Export success, byte size and returned file metadata **do not establish page count**.
- Open/render the PDF and check **actual number of pages**, visual alignment, overflow, clipping and readability.
- If more than one page, suggest small permitted spacing/wording refinements, show impact and ask approval before removing substantial material. Never falsely label a two-page PDF as a one-page verified resume.
- If PDF tools are unavailable, explicitly return `PDF verification unavailable` rather than a fabricated page count/link.

## 6. Deliverables
- Provide Doc name and verified URL, PDF only if actually available, actual verified page count (or `not verified`), bullet-by-bullet change log, relevant JD evidence gaps and which original Base Doc remained intact.
- Resume generation does **not** imply job application, spreadsheet update or recruiter contact. Never submit or trigger an application.

## When a source is unavailable
- If Story Bank is missing, you may review the JD against source text the user supplied, but disclose limited evidence and request the Bank before claiming story-backed tailoring.
- If no Google connector, propose exact edits for user to apply; don't claim a document copy or one-page export.
